# Repo-Wide Archetype / System Framework Design

Date: 2026-03-14
Status: Drafted after user-approved design direction
Scope: Entire repo-wide archetype/system framework, with category canon, entry-writing standards, and implementation plan before code changes

## Purpose

This design redefines the repo-wide archetype framework so that `Systems` become the core progression identity layer rather than a loose collection of flavor-heavy archetypes. The framework must remain compatible with the current lore and world rules. In canon, `Void` and `Grandmother Void` sit above all structured power. Beneath them, `Systems` are the strongest active structures that can bind to mortals, vessels, hybrids, chosen heirs, and anomalies. The remaining categories exist beneath Systems as narrower or less stable expressions of structured power. The goal is not just to rename content, but to make the repo treat this hierarchy consistently across generated content, character creation, save state, prompt assembly, quests, and progression systems.

## Current Repo Surfaces

The framework currently spans multiple runtime layers and cannot be treated as a Godot-only content tweak.

- Godot local content: `godot/data/character_options.json`
- Godot creation flow: `godot/scripts/character_creation_controller.gd`
- Godot creation UI: `godot/scripts/character_creation_panel.gd`
- Generated creation content pack: `packages/game-core/src/data/generated/character-creation/archetype-systems.json`
- Content pack accessors: `packages/game-core/src/characterCreation/CharacterCreationContentPack.js`
- Canonical registry: `packages/game-core/src/systems/archetype/ArchetypeSystemRegistry.js`
- Character creation hook: `src/hook/useCharacterCreationReworked.js`
- Character creation UI mode: `src/ui/modes/CharacterCreationMode.jsx`
- Narrative and prompt wiring: `src/core/PromptAssembler.js`
- Quest wiring: `packages/game-core/src/systems/quest/QuestManager.js`
- Save and state shaping: `packages/game-core/src/core/StateNormalizer.js`

## Canon Hierarchy

### Void and Grandmother Void

`Void` and `Grandmother Void` are not gameplay-facing categories and should not be represented as ordinary player choices. They are supra-structural realities that define the upper boundary of what structured power can do at all. Nothing in the archetype/system framework can supersede them. Any content derived from the lower framework must explicitly respect this boundary. They act as cosmological ceiling, metaphysical source tension, and lore guardrail. They should shape narrative stakes, not the normal selection surface. Their existence prevents the framework from drifting into unrestricted omnipotence. They also justify why even the strongest System remains powerful but not absolute.

Possible uses: They should be used to define setting-wide hard limits and existential threats. They can anchor late-game or mythic quest arcs without becoming routine player power picks. They can also justify why some Authorities fail, why some Paths collapse, and why some Overlays trigger cosmic retaliation. In prompt and narrative systems, they should serve as forbidden reference points rather than normal mechanical assets.

### System

A `System` is the strongest complete progression structure beneath Void and Grandmother Void. It is not merely an ability package, item set, or class perk, because it carries its own internal progression logic, reward structure, and metaphysical interface rules. A System changes how the world yields opportunity, growth, danger, and reward to the bearer. It can coordinate multiple progression surfaces at once, including combat, quests, skill acquisition, crafting, contracts, loot, and identity. A true System should feel like an engine that is always interpreting the bearer and the world in relation to each other. Systems should be rare enough that cultures, factions, and institutions treat them as legendary, heretical, royal, apocalyptic, or sacred. Every System must include a protocol, bias, burden, or directional limitation so that it remains dominant without becoming narratively meaningless.

Possible uses: Systems should anchor the primary character-creation identity choice across the repo. They can also drive quest generation, narrative tone, loot weighting, progression pacing, and special reactions from factions. In runtime systems, they should be able to modify multiple gameplay surfaces without needing to be hardcoded into every subsystem. In narrative terms, they are the cleanest way to support strong light-novel and progression-fantasy fantasies like regression, devouring, copying, synthesis, omniscience, summoning, or transcendence.

### Authority

An `Authority` is a concentrated right of command over a domain, law, force, species, artifact class, bloodline channel, or metaphysical field. Unlike a System, an Authority is usually narrower in scope, but far more absolute within its rightful domain. Authorities feel regal, judicial, sacred, tyrannical, or ancient because they are fundamentally about permission and imposition. A bearer of Authority does not merely gain power, but is recognized by reality as someone entitled to command or suppress a particular thing. This makes Authorities especially dangerous in the lore, because a narrow absolute can overwhelm broad but shallow strength. Authorities therefore need domain limits, contest rules, or activation burdens so they remain fearsome without flattening the setting. They sit below Systems because they dominate locally, not across the bearer's full progression architecture.

Possible uses: Authorities are ideal for rulers, saint-level foes, late-game specialists, divine heirs, and restricted evolution branches. They can also function as secondary specialization layers beneath a System. Quest content can use Authorities to drive inheritance wars, domain conflicts, artifact claims, sacred trials, and law-breaking penalties. In narrative systems, Authorities provide high-signal social meaning because NPCs can recognize and fear them even when they do not understand a deeper System.

### Path

A `Path` is a transformation route that gradually changes what the bearer becomes. Paths are slower, steadier, and more stage-driven than cheat-style Systems because they demand repeated refinement, thresholds, awakenings, and crises. Where Systems often impose an external engine on the bearer, Paths feel like the bearer being rewritten by chosen pressure over time. A Path may be holy, corruptive, beastly, ascendant, dreamlike, necrotic, void-adjacent, or artifact-bound, but it always has visible consequences. These consequences should affect body, soul, instinct, worldview, social role, and access to later power states. Paths are highly compatible with cultivation arcs, monster evolution arcs, corrupted ascension arcs, and identity metamorphosis arcs. They sit below Authorities because they change the bearer profoundly without automatically granting sovereign command over a domain.

Possible uses: Paths are ideal for long-form progression ladders, realm systems, mutation trees, evolution branches, and identity shifts. They can be attached to races, cursed vessels, undead, cultivators, beast lines, and dream-walkers. They are also strong narrative tools because each stage can change faction reactions, body horror, romance dynamics, combat expectations, and moral pressure. In implementation, Paths map well to milestone triggers, stage thresholds, unlock tables, passive shifts, and branching specialization logic.

### Framework

A `Framework` is an organizing structure that governs power flow without always being the deepest source of power itself. Frameworks are infrastructural rather than sovereign. A Framework tells the bearer how power is stored, compounded, archived, inherited, accelerated, routed, or instantiated. This makes Frameworks ideal for dungeon administration, reincarnation mapping, save-state logic, training compression, quest chain compounding, blueprint forging, internal-world management, and reward protocol systems. A character with a Framework may not look overwhelming at first glance, but over time Frameworks create frighteningly orderly growth. Frameworks should feel procedural, architectural, and scalable. They sit below Paths because they optimize progression rather than always constituting the bearer's existential transformation.

Possible uses: Frameworks are perfect for support systems that touch many mechanics without needing to be the main identity engine. They can power management gameplay, downtime growth, recursive loot logic, storage rules, save-state mechanics, and automation-heavy progression. They are also excellent implementation surfaces because one Framework can influence quests, loot, progression pacing, crafting, and simulation hooks at once. In story terms, Frameworks justify how some characters become unbeatable through structure rather than raw spectacle.

### Privilege

A `Privilege` is a sanctioned exception, hidden entitlement, ancestral favor, illicit loophole, or narrow but unfair advantage. Privileges are smaller in scale than Systems and less architecturally dominant than Frameworks, but they are efficient and asymmetrical. A Privilege does not need to overpower the world broadly in order to distort outcomes decisively. It may reveal hidden information, secure unique class access, soften destiny, warn against lethal threats, or unlock content unavailable to ordinary participants. Privileges are often underestimated because they are subtle instead of spectacular. They should therefore produce leverage, hidden compounding, access asymmetry, or protected exemptions rather than blunt omnipotence. In the hierarchy, they sit below Frameworks because they are exceptions inside a structure, not the main structure.

Possible uses: Privileges are ideal for starting bonuses, hidden routes, prophecy logic, royal exemptions, stealth advantages, and secret quest triggers. They can differentiate similar builds by changing how a player navigates the same world rather than simply changing combat numbers. In narrative systems, Privileges support "chosen one," "villain advantage," "forbidden heir," and "fate-favored" story logic without requiring every such figure to possess a full System. In implementation, they fit well as modular modifiers on quests, loot tables, encounter generation, discovery, social checks, and failure recovery.

### Overlay

An `Overlay` is an unstable exploit layer that attaches itself to deeper structures and grants abnormal leverage through corruption, loopholes, desync, rollback, or interface distortion. Overlays are the most suspicious category because they feel ontologically wrong. They often resemble cheating not only socially but cosmically, because the world itself registers their effects as malformed or out-of-band. This makes them perfect for glitch powers, corrupted UIs, broken quest states, temporal rollback fragments, cost bypasses, or impossible combat timing abuse. However, Overlays must always create instability, backlash, pursuit pressure, identity drift, or collapse risk. Without these costs, they stop being Overlays and become merely overpowered Systems. They sit lowest in the hierarchy not because they are safe, but because they are parasitic, unstable, and dependent on deeper laws.

Possible uses: Overlays are excellent for corrupted protagonists, hidden bosses, forbidden subclasses, and desperate comeback mechanics. They can drive high-tension quests because every use can attract enforcers, system audits, cultists, or cosmic predators. In gameplay, they are strong homes for risk-reward mechanics like rollback windows, hidden menus, debug-state effects, and violent temporary spikes. In narrative terms, they let the setting depict power that is effective, uncanny, and spiritually alarming all at once.

## Entry Description Standard

Every individual system-framework entry should follow the same content contract so the repo can validate quality and so runtime systems can depend on consistent semantics.

### Required fields

- `id`
- `name`
- `category`
- `summary`
- `description`
- `possibleUses`
- `coreLoop`
- `progression`
- `narrativeHooks`
- `questHooks`
- `limits`
- `costs`
- `worldCompatibility`
- `tags`
- `progressionImpact`
- `implementationProfile`

### Description rules

The `description` field must be at least 7 sentences long. It must explain what the entry is, how it functions, why it belongs to its category, what its progression bias is, what its main tradeoff is, how the world perceives it, and what keeps it from invalidating the setting. Description text should prefer systems-first language over empty hype. It should describe protocols, rules, fuels, or metaphysical logic rather than only theme. It should also explain whether the entry is broad or narrow in scope. The text must be compatible with the canon hierarchy defined above. It must not imply that the entry can overrule Void or Grandmother Void. It must not lean on placeholder phrasing or vague "unlock further potential" filler.

### Possible uses rules

The `possibleUses` field must be at least 4 sentences long. It should describe where the entry can matter in gameplay, story, progression, and world interaction. At least one sentence must describe a gameplay use case. At least one sentence must describe a narrative or quest use case. At least one sentence must describe an implementation or systems use case. At least one sentence must describe a limitation-aware use case so the entry does not read as consequence-free power.

### Core loop rules

The `coreLoop` should explain how a bearer repeatedly interacts with the entry. Each step should be actionable and observable. A good core loop answers: what do you do, what do you gain, what do you risk, and what do you repeat. Loops should be short enough for UI preview and specific enough for quest and combat hooks. They should not be generic lines that could describe every progression system in the project. They should imply meaningful gameplay surfaces such as combat, economy, crafting, companions, knowledge, territory, or narrative leverage.

### Limits and costs rules

Every entry must declare limits and costs explicitly. Limits can include scope, target class, activation windows, domain restriction, corruption, social stigma, cooldown, resource drain, or compatibility rules. Costs can include fuel, reputation, trauma, instability, physical burden, soul degradation, attention from enemies, or narrative debt. If an entry lacks meaningful costs, its category placement should be questioned. Systems can be powerful, but they cannot be consequence-free. Overlays in particular should impose escalating consequences. Authorities should state what they cannot command and Paths should state what they force the bearer to become.

### World compatibility rules

Each entry needs a `worldCompatibility` block or equivalent description logic that explains how it fits current canon. This should describe whether the entry is legal, hidden, forbidden, royal, sacred, heretical, corrupted, or unknown within the world. It should also clarify which factions or institutions are likely to cultivate it, fear it, suppress it, or study it. Compatibility text must respect the cosmic order and should explain why the world has not already collapsed under the existence of the entry. This field is especially important for regression, devouring, infinite growth, and glitch-like content. It creates the bridge between flavor text and actual world rules. It also helps prompt systems and quest systems generate appropriate reactions instead of generic ones.

## Repo-Wide Implementation Plan

### Approach options

1. Recommended: preserve the current six-category repo structure and rewrite the framework semantics around the canon hierarchy above.
   This has the best compatibility with current code, generated data, UI panels, prompt assembly, and save shape.
2. Alternative: collapse the framework into fewer categories and refactor every dependent module accordingly.
   This would be cleaner conceptually, but it would create a larger migration surface and higher risk.
3. Alternative: keep the code structure but only update text and labels.
   This is the lowest-risk short term option, but it would fail to deliver a truly coherent repo-wide framework.

### Data model

The generated archetype-system data should become the source of truth for entry descriptions and hooks. Category semantics should be formalized in validation so entries cannot drift back into vague or contradictory meanings. Godot local content should not remain a disconnected mini-list of placeholder archetypes. Instead, the Godot slice should eventually consume a curated subset or generated derivative of the repo-wide canonical system definitions. Save-state shape should continue to store a stable system identifier and a resolved summary object. All runtime consumers should tolerate old saves via normalization and migration rules.

### Canonical entry schema

The safest implementation path is to preserve the existing `archetypeSystem` runtime field name for compatibility while upgrading the content contract behind it so it truly represents the system-framework hierarchy. The data schema should remain category-agnostic at the top level, but it needs richer fields that make lore, prompts, quests, and progression all consume the same canonical meaning. Existing fields such as `id`, `name`, `category`, `summary`, `description`, `coreLoop`, `progression`, `narrativeHooks`, `questHooks`, `tags`, `progressionImpact`, and `implementationProfile` should remain first-class. The following additions should become canonical rather than optional prose conventions: `possibleUses`, `limits`, `costs`, `worldCompatibility`, `activationModel`, `resourceModel`, `counterplay`, `progressionStages`, `factionReactions`, `rarity`, `stability`, and `selectionWeight`. Category-specific extensions should be allowed, but they should live under named sub-objects rather than freeform field sprawl. For example, `Authority` entries may carry `domainRules`, `Path` entries may carry `stageMutations`, and `Overlay` entries may carry `instabilityEvents`, but the shared contract should stay stable. A full entry should therefore be rich enough for UI previews, prompt assembly, quest generation, validation, and future memory extraction without forcing every system to be hand-special-cased in code.

Possible uses: This schema lets one piece of content drive character creation, narrator tone, quest hooks, faction reactions, and progression modifiers at once. It also gives validation a real target, so low-quality or lore-breaking entries can be rejected before they leak into generated packs. Because the runtime can keep storing `player.archetypeSystem`, migration risk stays low even while the meaning of the data becomes much stronger. It also creates a clean path to future structured narrator memory, because fields like `worldCompatibility`, `factionReactions`, and `progressionStages` are already shaped for selective recall instead of only prose display.

### Compatibility and aliasing

The repo should treat `archetypeSystem` as the compatibility field name and `system` as the presentation language. This means the UI, docs, and prompt text can say `System`, `Authority`, `Path`, and so on, while saves and normalization continue to accept `player.archetypeSystem`, `player.system`, or a minimal string id. State normalization should remain permissive on input and canonical on output. Output should always resolve to a rich object that includes `id`, `name`, `category`, `summary`, `description`, and the new structured fields needed for prompts and quests. Legacy saves that only carry a string id should be upgraded silently through registry lookup. Legacy saves that carry partially hydrated objects should be merged with canonical definitions rather than trusted blindly. This keeps old runs playable while allowing the canonical registry to become much more expressive.

Possible uses: This alias strategy avoids a costly rename across every reducer, selector, save slot, and prompt path in one pass. It also keeps Godot and web integration simpler because both can target the same canonical ids even if their local labels differ. For toolchains and future content generation, it means authors can think in terms of `system-framework entries` without worrying about backward-compat field names. It also reduces rollout risk because presentation improvements can ship before deep migration is complete.

### Validation

Validation should move beyond simple structural presence checks. It should enforce description length, possible-uses length, category-appropriate semantics, placeholder bans, and world-compatibility requirements. Validation should also ensure that a `System` entry is not accidentally written like a `Privilege`, or that an `Overlay` does not read like a clean lawful blessing. The validator should flag phrases that imply uncapped omnipotence without a declared cost. It should also verify that each entry exposes usable hooks for runtime systems rather than only marketing text. Generated reports should identify which entries fail the lore contract and why.

Validation should be split into three layers. The first layer is structural validation, which checks required fields, array lengths, and type shapes. The second layer is semantic validation, which checks sentence counts, placeholder bans, category fit, missing costs, and explicit respect for the Void hierarchy. The third layer is runtime usability validation, which checks whether the entry exposes the hooks needed by character creation, prompts, quest generation, and save hydration. Failing content should produce machine-readable reports grouped by file, id, and rule family. This matters because the registry is already central enough that bad content can leak into many surfaces at once. A validator that only checks shape is not enough for the kind of canon the user wants.

Possible uses: Strong validation will make the content pipeline safe enough to scale the entry library without losing canon discipline. It also gives the team a way to bulk-rewrite older entries while measuring progress instead of editing blindly. Since the project already has generated character-creation packs, validation can become the gate between authoring JSON and shipped runtime data. It also reduces prompt risk, because the narrator will no longer ingest shallow or contradictory system descriptions that make the world feel fake.

#### Category-aware validation matrix

Validation should explicitly encode what each category is allowed to mean. `System` entries must describe a full progression engine, state at least one governing cost or limitation, and explain why they are stronger than narrower categories without implying supremacy over Void or Grandmother Void. `Authority` entries must describe dominion over a bounded law, domain, force, lineage, or class of beings, and they must identify what contests or limits that command. `Path` entries must include stages, thresholds, or transformative checkpoints and must read like a route of becoming instead of a static perk package. `Framework` entries must describe infrastructure, organization, recursion, storage, training, routing, or persistence rather than personal supremacy. `Privilege` entries must describe a narrow asymmetric exception and should fail validation if they read like a whole game system in disguise. `Overlay` entries must describe instability, exploit behavior, and backlash, and should fail if they sound clean, lawful, or consequence-free. Across all categories, placeholder phrases such as `unlock further potential`, `ordinary powers cannot solve`, or other generic filler should fail semantically even when the JSON shape passes. This matrix should live next to the schema so content authors and tooling both know what category drift looks like.

Possible uses: This matrix gives implementation a direct rulebook for semantic linting instead of relying on human vibes during review. It also creates a clean bridge between the user’s lore requirements and the existing JSON pipeline, because now category fit is machine-checkable. For writers, it clarifies why a rewrite fails and how to fix it without guessing whether the issue is prose quality or canon mismatch. For runtime safety, it stops a bad entry from slipping into prompts and making the entire world hierarchy feel inconsistent.

### Character creation

Character creation should present Systems as the core identity layer and surface category context clearly. The main web flow already has richer system support and should become the canonical reference behavior. The Godot slice should eventually reflect the same category semantics, even if it exposes a smaller starter list. Recommendation logic should be category-aware, class-aware, race-aware, and lore-aware. Preview panels should explain not just what the entry is, but how it changes the player's likely run fantasy. The UI should stop treating all entries as flat "archetypes" and instead explain why a System, Authority, or Overlay feels different.

In the web flow, the current `selectedArchetypeSystem` path already gives a stable integration point. The main work is to enrich what gets previewed and stored, not to reinvent the whole selection step. The picker should expose category, rarity, stability, core loop preview, costs, world reputation, and a concise `run fantasy` explanation. The review step should summarize the selected system-framework entry in world terms rather than only repeating a short summary line. The output blueprint should also preserve structured system metadata that later systems can trust instead of only prose fragments. Godot should follow the same shape using a smaller curated subset generated from the canonical registry rather than maintaining a disconnected placeholder list.

Possible uses: This will make the player’s main identity choice feel like a true world-shaping selection instead of a checkbox. It also makes later systems easier to write because combat, quests, and narration can assume the chosen entry came from the same canonical contract. Since the web flow already stores the chosen object, the migration cost is mostly in richer previews and richer stored fields. It also means Godot can become a faithful starter interface rather than a lore fork.

#### Character-creation presentation contract

The web picker should present each entry with a stable five-part card contract: `name`, `category`, `run fantasy`, `cost or burden`, and `world classification`. Hover or detail panels should then expand into `core loop preview`, `possible uses`, `stability`, `rarity`, and two short `faction reaction` lines. The review screen should summarize the player’s choice as identity and consequence, for example `You are bound to a legendary System feared by institutions` rather than only restating a summary sentence. Category help text should be persistent somewhere in the flow so players understand why a `Privilege` is narrower than a `System` and why an `Overlay` is inherently unstable. Recommendation logic should rank entries using current race, class, origin, and stated player intent, but should never hide incompatible or risky options without explanation. Any entry blocked by lore compatibility should remain visible in the authoring or admin view with its failure reason so tooling stays honest. This contract should be shared by the web flow and any future generated character-creation docs or export surfaces.

Possible uses: This gives frontend implementation a concrete information hierarchy instead of a vague “make the picker richer” brief. It also helps onboarding, because players can read one card and immediately understand fantasy, cost, and social consequence. For content QA, it creates a stable set of fields that every new entry must be able to populate cleanly. For Godot alignment, it provides the template that a smaller curated picker should mirror instead of inventing a different mental model.

### Narrative and prompt systems

Prompt assembly should consume the new detailed descriptions, possible uses, and world compatibility fields. Narrative tone should not rely only on category labels, but on entry-specific worldview and consequences. Quest prompts should use the category to determine scale and social response, while the specific entry determines hook flavor. Story output should know the difference between a player carrying a true System and a player carrying a narrow Privilege. This will let the narrative layer produce more grounded reactions and better continuity. It will also reduce repetitive "system" language because the prompt will have more precise data to work with.

The narrator-memory audit shows that the live narrator remembers whatever the prompt builder and saved narrative state preserve, not whatever some hidden backend memory knows. That means prompt assembly is the highest-leverage place to upgrade immediately. The context section should add `possibleUses`, `limits`, `costs`, and `worldCompatibility` in compact summarized form rather than dumping the full long description every turn. The opening prompt should also surface `questHooks`, `factionReactions`, and one `consequence clause` so the narrator understands how the world should react to the chosen system. Summary refresh logic should later be upgraded to preserve system-relevant facts such as taboo violations, public exposure, milestone ascensions, faction hostility, and corruption signs. If the dormant `StoryMemory` layer is activated later, those same structured fields should become the source categories for durable memory extraction.

Possible uses: This lets narration become more lore-faithful without requiring a backend architecture rewrite first. It also creates the bridge between the system-framework rewrite and the narrator audit, because we now know exactly where continuity is being compressed. Since the current summary mechanism is already live, adding system-aware summary prompts can improve long-arc consistency quickly. It also prepares the project for future memory persistence without forcing that larger change into the first rollout.

#### Prompt payload contract

The prompt payload should stop at compact high-signal fields rather than dumping full entry prose. The current `PromptAssembler` already sends name, category, one summary line, and up to two narrative hooks, which is the right insertion point for a richer compact contract. The upgraded payload should add `system run fantasy`, `core loop preview`, `limits`, `costs`, `world compatibility`, `faction reactions preview`, `quest hooks preview`, `stability`, and `public exposure state` when known. `World compatibility` should be rendered as one short line that answers how the world classifies the chosen entry, for example `legendary taboo System`, `lineage-bound Authority`, or `unstable exploit Overlay`. `Limits` and `costs` should be rendered separately so the narrator can distinguish “cannot do” from “can do, but pays for it.” `Faction reactions preview` should be capped to two short clauses because the narrator only needs enough information to anchor social response, not a whole political essay each turn. `Public exposure state` should come from live game state rather than static entry data so the narrator can react differently to a hidden corruption path than to a notorious public one. If the summary system is upgraded later, these same compact fields should also be the categories retained in `narrative.summaryMeta` or any future `StoryMemory` extraction.

Possible uses: This contract gives prompt integration a concrete payload shape that is rich enough to matter but still small enough for every turn. It also means the narrator can finally distinguish between “this player has a dangerous authority” and “the world has publicly realized the player has a dangerous authority,” which are different story conditions. For engineering, it gives `PromptAssembler` and future summary code a precise field list to build and test against. For future memory work, it creates ready-made durable fact buckets instead of forcing memory extraction to reverse-engineer long prose later.

### Quests and progression

Quest generation should explicitly use system-framework hooks instead of treating archetype content as optional garnish. Systems should be able to emit milestone trials, rivals, category-specific tests, and progression forks. Authorities should drive domain conflicts, inheritance claims, or enforcement quests. Paths should drive breakthrough quests, transformation crises, and stage walls. Frameworks should drive recursive objectives, management loops, or optimization arcs. Privileges should unlock hidden routes and alternative resolutions. Overlays should create unstable, high-risk branches and enforcement pressure.

The existing `QuestManager` already uses `questHooks` and can generate a system directive quest, which is a strong base to extend rather than replace. The next step is to move from a single generic directive quest to category-aware quest builders. A `System` quest should feel like a core progression contract, an `Authority` quest should feel political or dominion-oriented, a `Path` quest should feel transformational, and an `Overlay` quest should feel volatile and hunted. Progression hooks should also be able to request milestone quests at specific conditions such as level thresholds, corruption thresholds, domain resonance, or public notoriety. This gives the framework real gameplay expression instead of leaving it trapped as text. It also keeps later balancing work grounded because category identity becomes mechanically testable.

Possible uses: This will let the same canonical entry influence both flavor and actionable gameplay. It also means category writing standards are no longer just lore standards, because quest output will expose shallow writing immediately. Since the current manager already resolves the selected system from player state, implementation can be incremental. It also creates a natural bridge to future faction-reaction systems, because quest offers and punishments can now key off the same canonical data.

#### Category quest-generation matrix

`System` quests should produce origin-defining contracts, rival-system encounters, major milestone directives, and run-shaping branching decisions. `Authority` quests should produce inheritance disputes, domain defense, command challenges, and political enforcement reactions. `Path` quests should produce breakthrough trials, stage stabilization, mutation crises, and threshold rituals tied to transformation. `Framework` quests should produce setup loops, optimization projects, managed-environment problems, and recursive objective chains. `Privilege` quests should produce hidden-route opportunities, covert resolutions, rare exemptions, and exposure-management dilemmas. `Overlay` quests should produce unstable exploit chances, patch-enforcer pressure, containment breaches, and “use the exploit or preserve stability” decisions. Each quest builder should request at least one `cost`, one `counterplay`, and one `world reaction` from the chosen entry so quests cannot drift into flavorless generic errands. This matrix should become both a design guide and a test expectation for `QuestManager` outputs.

Possible uses: This matrix translates the category hierarchy into actionable quest behavior with almost no ambiguity left for implementation. It also gives testing a category-by-category expectation set, which is much easier to verify than “the quest should feel right.” For writers and designers, it clarifies what sort of conflict each category naturally wants to generate. For future balancing, it prevents one category from accidentally stealing the dramatic role of another because the quest grammar is now explicit.

### Save compatibility and migration

Existing saves that reference `archetypeSystem` should remain valid through normalization. The normalizer should resolve old IDs into rewritten canonical entries without breaking player state. Where descriptions or fields are expanded, fallback defaults should be derived from category-level rules to avoid null behavior. Migration should be additive first, destructive later if needed. Any renames should preserve alias maps or compatibility lookups. Save migration must be treated as part of the design, not as cleanup after implementation.

Migration should happen in three tiers. Tier one should normalize old string ids into full canonical objects with compatibility aliases preserved. Tier two should backfill missing structured fields such as `possibleUses`, `limits`, `costs`, `worldCompatibility`, and `implementationProfile` from the registry when the saved object is partial. Tier three should optionally mark the hydrated object with a `contentVersion` or `schemaVersion` so later systems can detect whether a run predates the new canon contract. At no point should the migration trust stale freeform descriptions over canonical registry data when a matching id exists. The canonical registry should be the repair source, while the save only contributes player-specific state such as chosen id, exposed milestones, current corruption, or other mutable progress. This keeps runs stable while preventing ancient placeholder content from continuing to pollute the narrator and quest systems.

Possible uses: This approach protects player progress while still letting the repo evolve aggressively behind the scenes. It also avoids hand-writing one-off migrations for every entry rewrite, because the registry becomes the default repair tool. Since the current normalizer already resolves ids into canonical entries, much of the migration path already exists conceptually. It also creates a clean place to add future story-memory migration if the dormant `StoryMemory` model is activated.

### Godot alignment

The Godot slice is currently the most visibly out of sync with the repo-wide framework. Its local `archetype` step should eventually be replaced with a canonical `system` selection layer that reflects the true lore hierarchy. The first alignment should be content-level and label-level. The second should be data-shape alignment so Godot stores identifiers and summaries compatible with the main framework. The third should be narrative and quest alignment so the chosen system affects prose, reactions, and progression. Godot does not need the full giant registry at once, but it should stop inventing placeholder semantics that contradict the repo canon.

#### Godot curated subset rules

The Godot picker should be generated from canonical entries rather than edited by hand, using a small whitelist file or build script input that points at canonical ids. The first subset should skew toward `System` entries, then include at least one representative `Authority`, `Path`, `Framework`, `Privilege`, and `Overlay` so the hierarchy is visible even in the smaller client. Every included entry should export `id`, `name`, `category`, `summary`, `runFantasy`, `costs`, `limits`, and two hook previews, with a content version stamped into the generated file for migration safety. Godot save data should continue storing the selected id plus a compact resolved summary object, never a disconnected local-only definition. If the canonical entry changes, Godot should refresh its derived subset on the next content sync rather than carrying stale prose forever. The old hardcoded placeholder archetypes should be removed only after the generated subset and migration lookup both exist. This keeps Godot small and stable while making it a faithful downstream consumer of the same canon as the web app.

Possible uses: This gives implementation a low-risk bridge between today’s Godot content and the future shared registry. It also keeps the Godot client light, because it only needs a curated derivative rather than the full authoring payload. For migration, it gives us a clean place to map old local selections onto canonical ids. For QA, it means the Godot subset can be snapshot-tested against the source canon on every generation pass.

### Runtime consumer map

The current runtime consumers can be grouped into five integration classes. Registry and validation live in `packages/game-core/src/systems/archetype`, where canonical content is loaded, normalized, scored, and exposed. Character creation consumers live in `packages/game-core/src/characterCreation/CharacterCreationContentPack.js` and `src/hook/useCharacterCreationReworked.js`, where the player selects and stores the chosen system entry. Prompt and narrative consumers live in `src/core/PromptAssembler.js` and `src/hook/narrative`, where the selected entry affects opening prompts, turn prompts, narrative tone, and summary continuity. Quest consumers live in `packages/game-core/src/systems/quest/QuestManager.js`, where `questHooks` already feed system directive generation. State and save consumers live in `packages/game-core/src/core/StateNormalizer.js`, autosave logic, and sync layers, where the chosen system object is rehydrated and persisted. This map matters because it shows the framework rewrite is cross-cutting, but also that every integration point already exists in a minimal form.

Possible uses: This consumer map gives us a safe rollout order, because we can harden the registry and validation first, then upgrade readers one layer at a time. It also makes testing easier because each integration class can get its own fixtures and assertions. Since the project already resolves and stores selected system data, the problem is mostly content richness and consumer expectations rather than missing plumbing. It also means the future implementation can be sliced into independently shippable workstreams instead of one risky mega-patch.

### Shippable workstreams

#### Workstream 1: Canonical schema and validator

Expand the shared schema to include the new canonical fields and add semantic validators for sentence counts, cost declarations, world compatibility, and category fit. Update the registry normalizer so partial content is repaired into the new shape where possible, but weak content still fails validation in authoring and generation pipelines. Add alias-aware readers so old entries and saves still resolve.

#### Workstream 2: Content rewrite and generation pipeline

Rewrite the canonical JSON entry sets for the six categories to the new standard. Add any generator or pack-build steps needed so the character-creation subset is derived from the canonical entries rather than maintained manually. Establish a curated starter subset for Godot and the web picker.

#### Workstream 3: Character-creation integration

Upgrade preview cards, detail panels, and review summaries to use the richer fields. Keep `selectedArchetypeSystem` as the compatibility state path, but surface `System` terminology and category distinctions throughout the UI. Ensure the final blueprint stores the fields required by prompts, quests, and later progression logic.

#### Workstream 4: Prompt and narrator integration

Upgrade prompt assembly to use compact system-framework summaries that include category, core loop, limits, costs, world reputation, and hook previews. Update summary refresh behavior so system-relevant developments are retained more reliably. Decide whether to activate the dormant `StoryMemory` plumbing now or defer it behind a second-phase memory project.

#### Workstream 5: Quest and progression integration

Replace the generic system directive behavior with category-aware quest builders and milestone triggers. Connect `progressionStages`, `counterplay`, `activationModel`, and category semantics to actual quest generation and later combat/progression hooks. Keep the first pass lightweight enough to ship without requiring a total quest-system rewrite.

#### Workstream 6: Save, sync, and Godot alignment

Backfill missing system data during state normalization and confirm that autosave, save/load, and synced run state preserve the richer objects safely. Then align Godot to a curated canonical subset that uses the same ids, summaries, and category semantics. Godot should become a consumer of canon, not a separate authoring surface.

### Testing and verification

Testing should mirror the workstreams rather than being left as an end-only checklist. Schema tests should verify structural and semantic validation with both good and bad fixtures. Registry tests should verify deduplication, alias resolution, quality scoring, and fallback hydration. Character-creation tests should verify that selected systems survive rerolls, review, blueprint generation, save/load, and opening narration generation. Prompt tests should verify that compact system context, costs, world compatibility, and hook previews are included and that history limits still hold. Quest tests should verify category-aware hook generation and legacy fallback behavior. Save tests should verify that old string ids, partial objects, and full canonical objects all normalize into the same expected shape.

Possible uses: This test plan makes the rollout safe enough to do incrementally without losing confidence between phases. It also gives the content rewrite a real definition of done, because entries are not valid merely when they look flavorful in a file. Since the narrator depends so heavily on prompt context, prompt assertions are especially important here. It also gives Godot alignment a safety net, because the canonical subset can be snapshot-tested against the same source definitions as the web flow.

### Recommended rollout order

The recommended rollout order is: schema and validator, content rewrite, web character creation, prompt integration, quest integration, save hardening, and finally Godot alignment. This order minimizes player-facing breakage because the canonical content becomes reliable before more consumers depend on it. It also keeps the narrator improvements close to the content improvements, which matters because the current narrator is state-and-prompt driven rather than backed by a true memory system. Godot should intentionally come later because it is currently the most divergent consumer and the easiest place to accidentally duplicate logic. The dormant `StoryMemory` plumbing should be treated as optional phase two unless prompt and summary improvements prove insufficient. That gives the project a clean first ship and a clear second ship rather than one oversized refactor.

## Narrator Memory Audit

### What the narrator currently receives

The active narrator is primarily prompt-driven rather than backed by a dedicated long-term memory layer. The main prompt builder assembles a compact state snapshot from `src/core/PromptAssembler.js`, and that snapshot is what the AI sees as its operative memory on each turn. The prompt includes player identity, level, secondary class, alignment, creation perks, starter trees, skill loadout, HP, mana, XP, current zone, current location, equipment, inventory, active quests, magic-state details, world flags, and the currently selected archetype/system including name, category, summary or description, and up to two narrative hooks. It also includes the current dominant narrative mood and a short anti-repetition directive derived from recent narrator lines. This means the narrator does not remember the world independently; it remembers whatever the current game state still exposes. The system is therefore state-continuity-driven, not persona-memory-driven. It is strong at short continuity and weak at deep selective recall unless that recall is preserved in state or summary form.

Possible uses: This current model is good for deterministic narration because the AI is always grounded in concrete state rather than private invented memory. It also means the future system-framework rewrite can immediately improve narration just by enriching the structured data passed into prompt assembly. The downside is that subtle long-arc facts can vanish if they are not represented in the summary, recent history, quests, flags, or another durable state field. This makes the narrator audit directly relevant to the system-framework plan, because richer system descriptions and world-compatibility fields should become part of the durable prompt context rather than relying on raw prose drift.

### What is kept in runtime state

The React runtime keeps a local `narrative` block in game state that acts as the narrator's practical memory buffer. That block currently stores `summary`, `entries`, `sequence`, and in active runtime also `summaryMeta` and `currentMood`. New narrator lines, system lines, and status-update lines are appended into `narrative.entries`, and the dominant mood is recomputed from those entries. The summary is refreshed periodically from the recent narrative and system lines, which gives the app a compact memory surrogate even when the full log grows. The UI uses that same state to show the summary, recent entries, and latest line, so the visible "memory panel" is really the current narrative log rather than a separate cognitive store. Because the normalizer spreads unknown narrative properties forward, `summaryMeta` and `currentMood` can survive normalization even though they are not part of the original bare initial-state shape. This means the narrator's memory is best understood as state-backed recap plus a rolling local transcript.

Possible uses: This runtime structure is already enough to support system-aware narration if the system framework starts writing better hooks into state. It also gives a clean place to inject future durable narrative facts such as faction impressions, known threats, taboo violations, or system milestones without inventing a second unrelated memory format. Since summaries are already refreshed from recent entries, the framework can later teach that summarizer to preserve lore-critical system consequences instead of only scene flavor. The main caution is that anything not promoted into state, summary, quests, flags, or another persistent structure is likely to fall out of narrator recall after enough turns.

### What is cached and persisted

The app also uses a small in-memory `initialNarrativeCache` keyed by starting scene, quest ids, and core character identity fields such as race, class, and profession. That cache exists only to avoid regenerating the opening narration repeatedly, and it is not a general story-memory feature. Separately, local autosave persistence writes the entire game state snapshot to local storage, which includes the `narrative` block and therefore preserves summary, entries, mood, and related narrative metadata across resume flows. Because autosave saves the whole state rather than a specialized story-memory object, narrator continuity survives save/load as long as the relevant facts are already present in the saved state. Server-side sync and save systems can also preserve that same game state because they store the run state, not just combat or inventory fragments. In other words, the narrator currently persists by piggybacking on full game-state persistence rather than through a dedicated memory subsystem. This is functional, but it means narrative memory quality is only as good as the data model of the main state.

Possible uses: This save-backed persistence is enough to keep narrative continuity stable across sessions today. It also means the future archetype/system framework can improve narrator recall without inventing a new save format if it stores richer system-facing state in the main snapshot. The weakness is granularity, because the system cannot yet save named memory facts, priorities, or selective recall categories separately from the general run state. If the project later wants stronger narrator memory, it should decide whether to continue enriching the main state model or actually activate the dormant story-memory schema described below.

### What exists on the backend today

The backend narrate endpoints in `functions/lib/handlers.js` do not currently maintain a long-term story memory for narration. The synchronous `/api/narrate` route simply runs narration from the submitted prompt and returns the result. The streaming `/api/narrate-start` and `/api/narrate-poll` flow creates short-lived `threadId` and `runId` records and stores only polling-oriented run data such as status, done flag, mode, returned narrative, mood, suggestions, output hash, error state, and expiry. Those run records are managed by `functions/lib/narrate-runs-store.js` and expire after a short TTL, so they are transport state rather than narrative memory. The backend narrator therefore behaves as a stateless generator whose continuity depends on the prompt provided by the client. This matches the `narrator_adk/agent.py` instructions, which explicitly treat the provided game state as the source of truth rather than referencing a separate memory vault.

Possible uses: This backend shape is good for reliability because it keeps narration infrastructure simple and avoids hidden state causing desync between client and server. It also means the system-framework rewrite can focus first on better prompt inputs rather than having to untangle an opaque memory service. The tradeoff is that no server-side recall exists for facts that fall out of the client-provided state snapshot. If later chapters need deeper selective memory, the team can either enrich prompt state further or add an explicit memory layer with clear ownership and sync rules.

### Dormant StoryMemory plumbing

The repo does already contain generated Data Connect support for `StoryMemory`, including `ListMyStoryMemories` and `UpsertStoryMemory`. The generated types show a per-run memory model with fields for `id`, `runId`, `memoryKey`, `memoryJson`, `lastSeq`, `createdAt`, and `updatedAt`. However, the current application code and narrator runtime do not appear to call these operations in the active narration path. That means the schema support exists, but it is not currently shaping what the narrator remembers. This distinction matters because it gives the project an implementation option without pretending the feature is already live. For planning purposes, `StoryMemory` should be treated as available infrastructure, not existing behavior.

Possible uses: If the project wants true long-arc narrator recall, the dormant `StoryMemory` model could be activated for curated memory categories such as unresolved vows, major system evolutions, faction enmities, soul wounds, or discovered cosmic truths. It could also support memory compaction by storing structured facts instead of relying only on ever-growing prose summaries. The key implementation decision will be whether those memories are narrator-only, gameplay-relevant, or both, because that affects validation, sync, and save migration. Until then, the live narrator should be described honestly as prompt-and-state driven with short-lived run polling and no dedicated active memory store.
