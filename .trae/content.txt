## 4. Web Adapter / UI Layer

### Hook: `useGameEngine` — [src/hook/usegamestate.js](src/hook/usegamestate.js)
- Imports from `src/core/` shim paths (which re-export from `@voidverse/game-core`)
- Uses `useReducer(gameReducer, initialGameState)` directly
- Subscribes to `SimBridge` events and forwards to dispatch
- Uses `SystemEventObserver.evaluate()` to detect state transitions
- Returns: `{ state, dispatch, dispatchSystemEvent, chatLog, addSystemMessage, setState, evaluateQuestProgress }`
- **Does NOT use `createSystemEngine`** — imports `gameReducer` directly into `useReducer`

### Hook: `useNarrative` — [src/hook/useNarrative.js](src/hook/useNarrative.js)
- Imports `parseAction`, `validateActionComprehensive`, `executeAction` from `src/core/` shim paths
- Also imports `assemblePrompt`, `generateNarrative` from `AIService` and `PromptAssembler`
- Builds action suggestions based on state
- ~581 lines, manages AI narrative flow

### Import pattern
All `src/core/`, `src/systems/`, `src/data/`, `src/utils/`, `src/util/`, `src/world/`, `src/simulation/`, `src/entities/`, `src/constants/`, `src/observability/` files are **back-compat shims** that simply do:
```js
// Back-compat shim: implementation lives in @voidverse/game-core.
export * from '@voidverse/game-core/core/ActionDispatcher.js';
```
This means the entire codebase under `src/` imports through these shims, which forward to `packages/game-core/src/`. The extraction to the monorepo package is **complete** — `src/` only contains shims + React UI/hooks.

## 13. EventBus

There are **two distinct EventBus implementations**:

### Core EventBus — [packages/game-core/src/core/EventBus.js](packages/game-core/src/core/EventBus.js)
- Global singleton with `Map` of listeners
- API: `on(event, handler)`, `off(event, handler)`, `emit(event, payload)`, `clear()`
- `emit()` is wrapped in `withTraceSpan` for observability
- Automatically forwards events to `SimBridge.emitEvent()` via `logToSimulation()` — maps `effect:applied`, `effect:removed`, `combat:*` to typed simulation events
- Exported as both individual functions and namespace object

### Simulation EventBus — [packages/game-core/src/simulation/events/EventBus.ts](packages/game-core/src/simulation/events/EventBus.ts)
- TypeScript class-based implementation (~512 lines)
- Full-featured: `subscribe()`, `subscribeToAll()`, `publish()`, `getEventLog()`, `clearLog()`, `queryEvents(filter)`, `getSnapshot()`
- Typed with `Event`, `EntityId`, `Tick` from `../types/core`
- Maintains internal event log (max 10000 entries) with filter/query capabilities
- Used by `SimulationContext` internally

## Summary of Key Findings for SystemEngine Architecture

### What's Already Done:
1. **Monorepo extraction is complete** — all game logic lives in `@voidverse/game-core` with `src/` shims
2. **`createSystemEngine` exists** but is a thin Phase 1 wrapper (4 functions, no config)
3. **`@voidverse/game-schemas` provides TypeScript types** for actions and state
4. **Simulation bridge architecture** provides seeded PRNG, event logging, replay capability
5. **Two EventBus implementations** coexist (core JS global singleton + simulation TS class)

### Gaps for Full SystemEngine Architecture:
1. **`createSystemEngine` is not consumed** by `useGameEngine` or `useNarrative` — they import core modules directly
2. **No `EngineConfig`** type or configuration injection — engine is always created with defaults
3. **No formal adapter interface** — `createSystemEngine` doesn't accept platform-specific providers
4. **`gameReducer` is tightly coupled to React's `useReducer`** in `useGameEngine` — not mediated through the engine
5. **Empty placeholder systems**: `cultivation/`, `stats/`, `ui/` in game-core
6. **`sim_gamestart_fixed.js` doesn't use game-core pipeline** — has its own simulation loop
7. **State shape is "intentionally loose"** per game-schemas comments — canonical state split not yet introduced
